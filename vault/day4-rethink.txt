# Day 4 Retink

Session 1 should be built as a **notebook exercise with two lanes**:

* the **core lane** is practical, guided, and notebook-based for everyone
* the **stretch lane** is a `.py` version for those more confident with Python

That works well.

## What Session 1 does

It gets learners to turn **silent failure scenarios** into **explicit checks in the pipeline**.

Not a lecture on validation.
Not `assert` as the main idea.

The practical outcome is:

* learners add a small set of checks to the HomeSphere pipeline
* they decide what the check is protecting against
* they decide what should happen if it fails

## A good session shape

### Part 1 - Frame the problem

Very short whole-group start.

Show 3 or 4 realistic silent failures from the HomeSphere pipeline:

* row count unexpectedly drops
* date parsing changes silently
* unmatched `product_id`
* numeric coercion creates nulls

Then ask:

* what went wrong?
* what check would catch it?
* where should that check happen?

Keep this short. Its job is only to set up the practical.

### Part 2 - Demo the first check

Do one check live in the notebook.

For example:

* check `silver_sales` has at least one row
* if not, raise a clear error or print a failure message and stop

This gives the less confident learners a pattern to copy.

### Part 3 - Notebook exercise

Learners work in the notebook on 3 or 4 TODOs.

For example:

#### TODO 1 - Row count sanity check

Check that `silver_sales` is not empty.

#### TODO 2 - Key field null check

Check that `product_id` is not null in `silver_sales`.

#### TODO 3 - Join quality check

After joining, check whether any sales rows did not match a product.

#### TODO 4 - Value sanity check

Check that `quantity` and `line_value` are sensible.

The key is that each TODO should include:

* **risk**
* **check**
* **what should happen if it fails**

So they are not just writing code - they are thinking operationally.

## How the notebook should look

I would structure it like this:

### Markdown cell

**Risk:** Sales file arrives with fewer rows than expected
**Task:** Add a row count sanity check before promoting to silver

### Code cell with starter

```python
row_count = len(silver_sales)

# TODO: check row_count and respond clearly if it is too low
```

Then repeat the same pattern for the other checks.

That keeps it accessible.

## What to use instead of `assert`

Do not make `assert` the main pattern.

Use simple explicit logic such as:

* `if ...: raise ValueError(...)`
* or collect failed checks and print a summary
* or set a `validation_passed` flag and stop promotion to gold

The teaching point is:
**pipeline checks should be explicit and readable**

## Stretch lane for confident learners

a `.py` file is a good stretch.

But it should be clearly framed as:
**same thinking, cleaner reuse**

The stretch task could be:

* move the notebook checks into a Python function or small validation script
* return pass/fail plus a message
* optionally make it reusable across different dataframes

For example:

* `check_not_empty(df, name)`
* `check_no_nulls(df, column, name)`
* `check_no_unmatched(left_df, right_df, key)`

That is a good stretch because it pushes them towards reusable validation logic without changing the core session for everyone else.

## What you do with the less confident learners

While stronger learners move into the `.py` stretch, you stay with the main notebook group and help them:

* complete the TODOs
* understand why each check matters
* decide what the pipeline should do when a check fails

So the session still works for mixed ability.

## What learners should leave with

By the end of Session 1 they should have:

* a notebook with a few working validation checks
* a clearer sense that “pipeline worked” is not enough
* a basic pattern for making failures visible
* for stronger learners, a small `.py` validation script or function set

## My recommendation on timing

pushing the documentation activity slightly later is sensible if this session needs close to an hour.

This one is worth the time because it gives them something concrete in the pipeline itself, not just discussion.

## In one line

**Session 1 should be a guided notebook exercise where learners add practical checks to catch silent failures, with a `.py` refactor as stretch for stronger Python learners.**
